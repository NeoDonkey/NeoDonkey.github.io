Git as Database: Why Version Control Beats SQL for Business Logic

By NeoDonkey Team · August 2026 · Technical

**Git as Database: Why Version Control Beats SQL for Business Logic**

*An open‑source ERP perspective*

---

1. The trouble with using a SQL database for business logic

When an ERP system stores its rules, workflows, and configuration in a relational database, developers quickly encounter three recurring pains.

**Schema migrations are fragile.**

A change to a table — adding a column, renaming a field, splitting a lookup — requires a migration script that must be run in every environment. If the script fails halfway, the database can be left in an inconsistent state, and rolling back often means restoring from a backup or writing a compensating script. Over time the migration history becomes a tangled web of conditional logic that is hard to audit.

**ORMs add indirection and opacity.**

Object‑relational mappers promise to hide SQL, but they introduce their own layer of abstraction. Queries that look simple in the model layer may generate inefficient joins, unexpected lazy‑loads, or hidden transactions. Debugging a performance issue frequently means stepping through generated SQL that bears little resemblance to the original code. Moreover, the mapping between domain objects and tables must be kept in sync; a missed annotation can silently corrupt data.

**Audit trails are patchwork.**

Regulatory compliance and internal governance demand a clear record of who changed what and when. Most SQL databases provide transaction logs, but they are low‑level, binary, and tied to a specific engine version. To produce a human‑readable history you must build extra tables, triggers, or change‑data‑capture pipelines. Those additions increase surface area for bugs and often miss edge cases such as schema‑only changes or failed transactions that still leave a trace in the log.

Together, these issues mean that the database — meant to be a reliable store of facts — becomes a moving target for the very logic it is supposed to support.

---

2. How Git solves those problems naturally

Git was designed to track changes to plain text over time. When we treat business logic as text files, many of the database‑related headaches disappear.

**Immutable history is built‑in.**

Every Git commit records a snapshot of the entire repository state, identified by a cryptographic hash (SHA‑1 or SHA‑256). Once a commit is created, its contents cannot be altered without changing the hash, which would break the chain of parent pointers. This gives us an append‑only log that is tamper‑evident by design — exactly what an audit trail needs.

**Branching gives safe experimentation.**

In a SQL world, testing a schema change often means copying the database, applying migrations, and hoping the copy stays in sync with production. With Git, a developer creates a branch, makes the desired edits to the rule files, and can run the full test suite against that branch without touching the main line. If the experiment fails, the branch is simply discarded; if it succeeds, a merge brings the changes forward with a clear, reviewable diff.

**Cryptographic signatures provide non‑repudiation.**

Git supports GPG‑signed commits. When a contributor signs a commit, anyone can verify that the commit originated from that private key and that the contents have not been altered after signing. This gives a stronger guarantee than a database user‑name column, which can be spoofed or altered by someone with sufficient privileges.

**Plain text enables tooling.**

Because the logic lives in files that any editor can open, developers can use diff tools, static analysers, and linters directly on the business rules. There is no need to translate between an ORM model and a SQL schema; the source of truth is the file itself.

3. Real comparison: database transaction log vs. Git commit graph

| Aspect | Typical SQL transaction log | Git commit graph |

|--------|----------------------------|------------------|

| **Granularity** | Records low‑level page changes; often opaque to humans. | Records whole‑tree snapshots; each commit shows a readable diff of files. |

| **Immutability** | Log entries can be truncated or purged according to retention policies; internal rewrites are possible with superuser rights. | Once a commit is made, its hash is fixed; altering history requires rewriting all descendant commits, which is evident to anyone with the repository. |

| **Branching & merging** | Not native; you must copy the database or use logical replication to isolate work. | Branches are lightweight pointers; merging creates a explicit merge commit that shows exactly what changed. |

| **Signature & verification** | Relies on database authentication; no built‑in mechanism to cryptographically bind a change to a person. | GPG signatures can be attached to any commit, providing verifiable provenance. |

| **Human readability** | Requires log‑mining tools or conversion to SQL statements; still tied to a specific engine version. | Plain‑text diffs are readable in any editor; no special tooling needed to understand what changed. |

| **Performance impact** | Logging adds I/O overhead; high‑transaction systems may need to tune log flush rates. | Writing a commit is essentially a file system operation; the cost is proportional to the size of the changed files, not the transaction volume. |

In practice, the Git commit graph gives you a *semantic* audit trail: you can see that “commit a3f9C2E added a new tax rule for region EU‑DE” rather than a cryptic page‑write entry. The graph also lets you visualise the evolution of a rule set over time, something that is cumbersome to derive from raw transaction logs.

4. “Git is the database” is an architectural choice, not marketing

Calling Git a database may sound provocative, but it reflects a deliberate shift in where the system of record lives. In a traditional ERP, the database stores both *state* (current inventory levels, open orders) and *logic* (workflow definitions, validation rules). By moving the logic into a version‑controlled repository, we separate concerns:

* **State** remains in a SQL (or NoSQL) store because it needs fast, concurrent updates and complex queries.

* **Logic** lives in Git because it benefits from immutability, traceability, and branching.

This separation is analogous to moving configuration files out of the database and into version control — a practice many teams already follow for application settings. The difference is that we extend the practice to *all* declarative business rules: pricing tables, approval workflows, data‑validation scripts, and even UI layout descriptors. The database continues to handle the mutable, transactional part of the system, while Git handles the immutable, versioned part.

From an architectural standpoint, the choice brings several concrete benefits:

1. **Deterministic builds.**

Given a specific commit hash, the entire set of business rules is known. Deploying that commit to any environment yields identical behaviour, eliminating “works on my machine” discrepancies caused by drift in stored procedures or triggers.

2. **Simplified CI/CD.**

A pipeline can lint, test, and sign the rule files, then promote the resulting commit through staging to production with a single merge. No separate migration step is needed for the logic itself.

3. **Reduced surface area for bugs.**

By eliminating ORM layers and stored‑procedure debugging, developers work directly with the files they edit. Fewer translation layers mean fewer places for mismatches to creep in.

4. **Compliance ready.**

Auditors can examine the signed commit history to verify that every change to a rule was reviewed, approved, and cryptographically tied to a responsible individual. No extra audit tables are required.

These are not buzzwords; they are measurable outcomes that stem from treating Git as the source of truth for the static, rule‑based portion of an ERP system.

5. How NeoDonkey implements this pattern

NeoDonkey is an open‑source ERP framework that puts the ideas above into practice. Its core design is simple:

* **Records are markdown files.**

Each business entity — such as a product, a customer contract, or an approval workflow — is represented by a `.md` file stored under a directory that mirrors the entity’s logical hierarchy. The file’s front‑matter (YAML) holds structured data (IDs, timestamps, references), while the body contains human‑readable descriptions, rules, or templates written in plain Markdown.

* **No ORM, no hidden mapping.**

When the application needs a piece of data, it reads the corresponding markdown file directly from the filesystem (or from an in‑memory cache populated at startup). Updates are performed by rewriting the file and committing the change. Because the file format is explicit, there is no need for a mapping layer that could drift out of sync.

* **Every change is a signed commit.**

NeoDonkey’s command‑line tool wraps Git operations. When a user creates, edits, or deletes a record, the tool stages the affected file(s), runs a pre‑commit hook that validates the markdown syntax and any embedded business‑logic scripts, then creates a GPG‑signed commit. The commit message follows a conventional format (`type(scope): short description`) that includes the record identifier, making the history searchable and machine‑parsable.

* **Branching for safe testing.**

A developer working on a new discount rule creates a feature branch, edits the relevant markdown files, runs the automated test suite (which loads the branch’s file set into a temporary runtime), and pushes the branch for review. The pull‑request discussion shows exactly which files changed and what the new rules look like, enabling non‑technical stakeholders to weigh in.

* **Merging becomes deployment.**

Once a pull request is approved, merging it into `main` triggers a CI pipeline that builds a release artifact. The artifact contains the committed markdown files; at startup, NeoDonkey loads them into its runtime store. No separate migration step is required because the logic is already versioned alongside the code.

* **Audit and verification.**

Because each commit is signed, anyone can run `git log --show-signature` to verify provenance. Regulatory reports can be generated by walking the commit graph and extracting changes to specific files, providing a tamper‑evident trail that satisfies most compliance frameworks.

This implementation shows that the “Git as database” idea is not a theoretical exercise; it is a working architecture that eliminates ORM complexity, gives a clear audit path, and lets teams use familiar Git workflows for business‑logic changes.

Closing thoughts

Treating Git as the source of truth for business logic removes a class of problems that have long plagued ERP systems: fragile schema migrations, opaque ORM abstractions, and incomplete audit trails. By keeping mutable state in a traditional database and immutable, versioned rules in Git, teams gain deterministic builds, safer experimentation, and cryptographically verifiable history — all without inventing new tooling.
