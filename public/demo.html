A running company, in five chapters.

This page is a guided tour of NeoDonkey doing its work: a chart of accounts adopted, an invoice issued, three posting legs written by a rule, an export a tax advisor can read. Nothing here is a mockup. The screenshots are real captures of the product, and every quoted line is real output from the kernel that ships in this repository.

The company is Weber Naturkost GmbH, a demo. It was seeded on 2026-08-22 in headless Chromium through the same kernel API the product uses, against the runtime vendored at pin 592a844.

Chapter 1 of 5

Your company is a git repository

Every act in NeoDonkey, creating the company, adopting the chart, issuing the invoice, is one signed git commit. The commit below is the one that posted the invoice you will meet in chapter 3. It is quoted from the workspace the screenshots were taken in: 

commit 9b04175722ac13fa4bb508b15ef33e0edef94e38
journal-entry JE-2027-0042 created

NeoDonkey-Transaction: v1
NeoDonkey-Actor-Roles: managing-director accountant controller tax-accountant category-manager customer-service-agent logistics-coordinator warehouse-clerk purchasing-manager
NeoDonkey-Change: create journal-entry JE-2027-0042
NeoDonkey-Change: create posting JE-2027-0042-receivable
NeoDonkey-Change: create posting JE-2027-0042-revenue
NeoDonkey-Change: create posting JE-2027-0042-output-vat
NeoDonkey-Rule: operating-model/processes/journal-posting.md:43
NeoDonkey-Rule: operating-model/processes/journal-posting.md:269

Three facts are in that message. The author signed it with an Ed25519 key that never left the browser. The four document changes landed atomically, in one commit. And the commit names the sentence of the operating model that permitted it, by file and line, which is what GoBD calls Nachvollziehbarkeit. Verification does not require our code: git log --show-signature answers it, and the acceptance test demo/sarah.mjs runs exactly that check with the real git and the real ssh-keygen.

Chapter 2 of 5

The interface is generated, not designed

There is no invoice page in our source tree. There is a declaration of what an invoice is, in operating-model/information/invoice.md, and the screen above is what the runtime renders from declarations like it: the fields, the references, the counts, and in the right hand column the operations the signed-in role may perform, read from the same text. Sarah Weber acts as managing director here because her signed peer record, peers/sarah-weber@local.json, says so. Change the text and the interface changes, which is why the operating model and not the screen is the product.

Chapter 3 of 5

Posting is a rule, not a form

When the accountant creates a journal entry she names the source document, the period and the chart. She does not choose accounts. Which accounts is a question the company answered once, in writing, in operating-model/processes/journal-posting.md: 

otherwise when journal-entry from a sales invoice then
  Create posting as "receivable"
    with position 1 with side "debit"
    with account-number from chart.receivables-account-number
    with amount from invoice.gross-amount
  and Create posting as "revenue"
    with position 2 with side "credit"
    with account-number from vat-treatment.revenue-account-number
    with amount from invoice.net-amount
  and Create posting as "output-vat"
    with position 3 with side "credit"
    with account-number from vat-treatment.output-vat-account-number
    with amount from invoice.vat-amount

The kernel executes that sentence. One commit later the entry carries three legs it did not arrive with, and the detail screen says where they came from:

An entry whose debits do not equal its credits cannot be committed at all; that invariant sits on the document declaration, not in interface code, so no screen can waive it.

Your tax advisor reads DATEV

Now the part other vendors leave out. As shipped at pin 592a844, this export fails. datev-extf.js asks the kernel for the postings of each entry with the query operator "is", and the kernel does not implement it. The error, reproduced during this capture, reads unknown operator "is" on field "journal-entry". The excerpt above was produced by rerunning the identical code with a one-line shim, "is" changed to "in". That shim is a reproduction aid, not a fix, and it is not committed anywhere. The defect is tracked as issue #134, and what it still owes is the fix and a regression test that drives the real query path, since the test that made gate 6 look green never exercised it. We would rather you read this paragraph here than discover it in your first export.

The honest part

What this page does not show

  • One user, one company, one month. Multi-peer sync exists in runtime/sync/ and is not exercised anywhere on this page.
  • The sales order was marked shipped by a signed update. The full picking chain, batch, quality release, stock movement, is modelled, and this capture did not walk it.
  • The DATEV excerpt relies on the shim disclosed in chapter 5. As shipped, the export throws. Treat the excerpt as the intended shape, not as a green gate.
  • The invoice render is a render. The field that would prove the customer received these exact bytes, archived-format-hash, is empty on this invoice.
  • The seeded chart is the model's own SKR04 table. The model itself instructs you to diff it against the current DATEV release before a real export, because DATEV renumbers between years.
