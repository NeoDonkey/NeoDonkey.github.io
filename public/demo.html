Chapter 1

Open a company

There is no account to create, no email to verify and no password to choose, because there is no server to log in to. You type your name; the browser generates an Ed25519 key pair on your machine, and your company begins as a git repository: a folder you own, or the browser's private storage if you prefer. The private key is non-extractable, so it never exists as bytes you could copy out.

Check: runtime/identity/ed25519.js, or open the program: /erp/index.html
Chapter 2

The screen is generated, not designed

Thirty-six kinds of document, forty-eight rules, thirteen roles, and not one hand-written invoice screen. The navigation, the tables and the permission badges you see here are generated from the operating model, a set of markdown files that live in the company's own repository. Change a sentence and the screen changes with it, which is why the interface can never drift away from the rules it enforces.

Check: the model ships with the program, at /erp/operating-model/
Chapter 3

The rules are sentences you can read

The operating model is not configuration and not code. It is prose with structure: ninety-three markdown files covering information, locations, organisation, suppliers, management reviews and processes. A rule reads like a sentence because it is one. And a model that cannot be read completely is never executed halfway: the runtime refuses it as a whole.

Check: operating-model/processes/journal-posting.md
Chapter 4

Every fact is a signed commit

Each business event becomes one git commit, signed with the key from chapter 1. The transaction log shows the chain, and the page offers the same check with tools we did not write: git log --show-signature and git fsck --strict in the company folder. The figure traces a new company's first commit: Demo User starts a company.

Check: runtime/git/
Chapter 5

Authorization is a rule, not a hidden button

The demo user in this figure holds no role, and the journal entry form says so before a single keypress: you may fill it in, and the operating model will refuse the write. It names the two lines that decide. Authorization is data in the repository, evaluated on every write, not a flag painted onto a button. Double-entry works the same way: debit and credit are separate required fields, and the books must balance or nothing is written.

Check: operating-model/information/journal-entry.md
Chapter 6

The invoice already speaks EN 16931

Net amount, VAT amount, VAT breakdown, payment means code, XRechnung profile: the invoice document carries the fields the European e-invoicing standard names, each one citing the line of the model that defines it. When the invoice is issued, runtime/export/xrechnung.js renders it as XRechnung XML, and runtime/export/datev-extf.js writes the ledger as a DATEV EXTF v700 batch for the tax advisor.

Check: runtime/export/

What this tour does not show

  • Sync. Two machines exchange commits directly over WebRTC, with no server in the middle, in runtime/sync/. It does not photograph: a picture of two laptops syncing is two pictures of a laptop. Open the program on two machines and watch.
  • Exports are modules, not yet buttons. The XRechnung and DATEV exporters run in the runtime today; the browser interface does not expose them as a menu item yet.
  • The company in these figures is empty. Zero documents, and a user with no roles granted, which is why chapter 5 shows a refusal. That is the honest first minute with the program, not a staged dataset.
  • The scorecard has the last word. What works and what does not is tracked in docs/GATE.md. If this page and the scorecard ever disagree, the scorecard is right.

Everything on this page is one click away from running in this tab. Opening a company takes about a minute, and the first thing it does is sign a commit with a key that never leaves your machine.
