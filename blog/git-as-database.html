Git Is the Database: How NeoDonkey Uses Cryptographic Commits as a System of Record

August 18, 2026 5 min read

Every ERP needs a database. Most choose PostgreSQL, Oracle, or SQL Server. We chose git.

Not "git for version control of our PostgreSQL schema." Not "git for backup." Git is the database. Every business fact in NeoDonkey is a commit. Every commit is cryptographically signed. The log is a real git log, readable by any git client on earth.

Here's why we made this choice and what it means for security, auditability, and sovereignty.

Why Git?

Git has properties that traditional databases don't:

  • Immutable history. Once written, a commit cannot be altered without changing every subsequent commit's hash. This is tamper-evidence built into the data structure.
  • Cryptographic integrity. Each commit is identified by a SHA-1 hash of its contents and its parent's hash. Change one bit, and the hash changes.
  • Branching and merging. Business operations often need parallel work streams — closing books while preparing next quarter's forecast, for example. Git's branching model supports this natively.
  • Universal tooling. Every developer knows git. Every CI system supports it. Every backup strategy works with it.
  • Offline-first. The entire repository lives locally. No network required for reads or writes.

Ed25519: Signatures, Not Permissions

Traditional ERPs use access control tables. User X has permission Y on resource Z. These tables live in the database, managed by administrators, and are vulnerable to privilege escalation, insider threats, and configuration errors.

NeoDonkey replaces access control tables with cryptographic signatures.

When you log in, your browser generates an Ed25519 key pair. The private key is non-extractable — it lives in the browser's Web Crypto API and cannot be exported. The public key becomes your identity.

Every commit you make is signed with your private key. Anyone can verify the signature with your public key. Authority is mathematical, not administrative.

gpg:                using EDDSA key 3A7B8C9D...
gpg: Good signature from "Marcus Weber <marcus@company.de>"

    Add supplier invoice #2026-0842

What This Means for Auditability

In a traditional ERP, auditing means running reports against a database and hoping the access logs weren't tampered with. In NeoDonkey, auditing means:

  • Running git log to see every change ever made
  • Verifying signatures with git verify-commit
  • Checking the hash chain for tampering
  • Using standard git tools: diff, blame, bisect

No proprietary audit module. No vendor consultant. No "trust us, the logs are fine." The audit trail is the data structure itself.

What This Means for Sovereignty

Your company's data lives in a folder. It's a git repository. You can:

  • Copy it to a USB stick
  • Push it to any git host (GitHub, GitLab, or your own server)
  • Encrypt it with GPG
  • Air-gap it on an offline machine
  • Read it with any git client, forever

There's no vendor holding your data hostage. No proprietary format. No "export fee." The repository is yours in the most literal sense possible.

"The best time to ensure you own your data was when you chose your ERP. The second best time is now."

The Technical Details

NeoDonkey implements git directly in the browser using standard Web APIs:

  • Origin Private File System (OPFS): A private, sandboxed file system accessible only to this origin. Your repository lives here, invisible to other websites.
  • Web Crypto API: Generates Ed25519 key pairs with extractable: false. The private key never leaves the browser.
  • CompressionStream: Efficient packfile compression, matching native git performance.
  • Plain ES modules: No framework, no build step, no dependencies. The git implementation is readable, auditable JavaScript.

The Trade-offs

This architecture isn't for everyone. Git excels at append-only, versioned data. It's not ideal for:

  • High-frequency transactional workloads (millions of writes per second)
  • Complex relational queries across many tables
  • Real-time collaborative editing (though branches and merges help)

For most SMEs — the companies NeoDonkey targets — these trade-offs are acceptable. The auditability, sovereignty, and simplicity benefits far outweigh the costs.

Conclusion

Choosing git as our database wasn't a gimmick. It was a deliberate architectural decision based on three principles:

  1. Data should be tamper-evident by default. Cryptographic hashes and signatures provide this.
  2. Authority should be mathematical, not administrative. Ed25519 signatures provide this.
  3. Data should be portable by design. Git's universal format provides this.

In a world of cloud lock-in and proprietary formats, git offers something rare: a database format that's been battle-tested for 20 years, that's universally understood, and that puts control back in the hands of the people who own the data.

That's why git is our database.
